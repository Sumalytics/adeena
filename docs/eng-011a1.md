# ENG-011A1: fixed public releases

The existing private version stays immutable and `unpublished`. A release is a
separate, owner-published snapshot referencing that exact version. Later edits do
not change the release. No Share UI or QR code is included in this task.

## Creator API

`POST /api/creator/releases` requires a verified Creator session and a same-origin
request. Workspace and publisher are derived on the server. JSON body:

```json
{
  "experienceVersionId": "<version UUID>",
  "approval": {
    "experienceVersionId": "<same version UUID>",
    "decision": "approved",
    "contentReviewed": true,
    "privacy": "no-identifiable-learner",
    "unresolvedHighRisk": false,
    "note": "Document the human review of this exact playable version."
  }
}
```

Returns `{ releaseId, playPath, replayed }`. Repeated publication of a version
returns the existing release without replacing its original evidence. Review
evidence is the owner's explicit attestation; it is not an automated safety
certificate. `ready-for-review` alone is insufficient.

Source rights must already be `cleared`. Normal uploads currently remain
`unverified`; this API cannot clear rights or override `review-required`, unsafe
topic flags, failed validation, or unaccepted edit proposals. Rights clearance
and resolving blocked reviews remain separate workflows. Do not change immutable
source rows to get around these gates.

`DELETE /api/creator/releases/<releaseId>` requires the workspace owner and a
same-origin request. It records revoker/time and is idempotent. Revocation is
one-way; publishing the same version again does not restore the release.

## Guest playback

`/play/r/<releaseId>` opens without a session. It loads the playable manifest from
`GET /api/releases/<releaseId>` using `cache: no-store`, then uses the existing
player. The database exposes only an active release's public manifest through a
narrow function; private tables retain RLS. Source identifiers, source metadata,
workspace IDs and approval evidence are not included. Private provenance remains
on the referenced version. The approved narrative itself is intentionally public.

The page's router payload contains no playable manifest. Page/API responses have
no-store headers. The client rechecks after visibility/page restoration and every
15 seconds while visible, removing the player if unavailable. New reads after
revocation return 404. Content already delivered to a learner cannot be recalled;
an open visible player notices revocation on its next check. Playback does not
invoke a model or spend generation credits.

## Database and validation

`0011_public_releases` adds the release table, owner RLS policies, eligibility and
immutability trigger, and the narrow guest-read function. It does not rewrite old
migrations or alter the version publication constraint. The migration runner
registers the new up/down scripts. Reversing it deletes release records.

Apply through the existing administrative migration workflow only when deploying
this feature; the application continues using `ADEENA_APP_DATABASE_URL` with the
restricted `adeena_app` role. The SECURITY DEFINER function follows the existing
administratively owned function pattern and requires its migration owner to be
able to read the FORCE-RLS table. No PUBLIC execute permission is granted.

`src/db/releases.test.ts` creates and drops its own randomly named disposable
database, using the configured admin connection only to create it. It tests real
RLS, rights/review restrictions, immutable releases, anonymous read/playback,
edit isolation, revocation, and migration reversal. The existing persistence
suite continues using its separate `adeena_test` database. Neither migrates the
persistent developer database.
